# IJ-SLM-1.0 model-specific adapter guide

Development starts from `reference/unchanged/1.0`. Load the explicit profile registry to select one adapter in a separate development arm. Save the profile and source hashes alongside model revision and hash, runtime build, binary hashes, SDK, GPU and backend, dataset, seed, case and run identifiers. Use the same model, scope and existing SDK policies in the paired arm. [Versioned switches](../atlas/slm/v1.0/sdk-adapter-profiles.json) · [Qualification evidence](SLM10_ADAPTER_QUALIFICATION.md)

## Integration boundaries

- Prompt Compiler and Action State require a digest pinned to the trusted SDK system message for the selected version. Action State uses tool and call IDs from audited visible callbacks in the current trusted scope. Its summary carries no result values or new permission.
- Compact Result Codec accepts a wrapper only when its tool, arguments, proposal, callback and value agree. Record source and transformed request hashes. Keep tool results in their tool message role.
- Construct Guard Authorization only after the SDK callback claim, duplicate call-ID checks, normal schema validation and current resource permission. The host attests a versioned immutable result and an explicitly redundant action. Legal repeats include forced refresh, the same arguments under a new action instance, and recovery after failure. Authenticate the current scope, keep storage local to one run and record the host reuse selection. Record actual delivery through the existing callback path.
- Apply Termination Policy to existing provider, SDK and workflow state. Continue processing proposals through the existing gates when the policy returns `CONTINUE`. Treat `BLOCK` as a failed or blocked output boundary with the original evidence recorded.
- Give Structured Output Contract the trusted public answer schema only after the existing terminal checks. Capture the raw output and validation verdict. Preserve the original model output in all quality metrics.

## Factorial admission

Freeze independent single-factor development comparisons and retain complete planned counts, including inapplicable or blocked cases. Score raw model proposals, native finish and answer, SDK callbacks, delivered content, host-protected callbacks, exact workflow outcomes, cancellation, audit and timing separately. A trigger without a measurable improvement in its declared role stays a single-factor research candidate. Reject any apparent benefit that requires lost authority, dropped required actions or incomplete output.

For LFM3, a prompt × codec study is a candidate if both single-factor cells improve the same target in matched development and fresh holdout cases. Use `(off, off)`, `(on, off)`, `(off, on)` and `(on, on)` with the same seeds and case roster. Freeze a separate profile for the combined arm. Leave a guard in a host-compensation comparison and track independent model quality. For Qwen3.5 and MiniCPM5, use the scoped single-factor comparisons above before deciding whether any combination is warranted. The current evidence establishes comparator design and software behavior. Factorial and physical qualification remain pending.
